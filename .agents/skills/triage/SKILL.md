# Triage

プロジェクトの issue tracker 上の issue を、小さな triage ロールの状態機械で動かす。

このリポジトリが外部 PR をリクエスト面として扱うなら（issue-tracker 設定を見る）、triage はそれも含む。**PR はコードが付いた issue**。同じロール、同じ状態、同じ機械。下の「PR の場合」と印した差分だけ。裸の `#42` は tracker 設定に従って issue または PR に解決する。

triage 中に issue tracker へ投稿するコメントや issue は、**必ず** この免責で始める:

```
> *This was generated by AI during triage.*
```

## 参照

- [AGENT-BRIEF.md](AGENT-BRIEF.md): 残るエージェント brief の書き方
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md): `.out-of-scope/` ナレッジベースの動き方

## ロール

2 つの **カテゴリ** ロール:

- `bug`: 壊れている
- `enhancement`: 新機能または改善

5 つの **状態** ロール:

- `needs-triage`: メンテナが評価する必要がある
- `needs-info`: 報告者からの追加情報待ち
- `ready-for-agent`: 仕様が揃い、AFK エージェントが取れる
- `ready-for-human`: 人が実装する必要がある
- `wontfix`: 対応しない

PR の場合、同じ状態を付いたコードに対して読む。`ready-for-agent` は brief が付き、エージェントが diff の次の一歩を取るべきこと。`ready-for-human` は人がマージする準備ができていること。

triage 済みの issue は、カテゴリロールちょうど 1 つと状態ロールちょうど 1 つを持つ。状態ロールが衝突したら、何もする前にフラグを立て、メンテナに聞く。

これらは正規のロール名。issue tracker で使う実際のラベル文字列は違うことがある。対応表は渡されているはず。なければ `/setup-matt-pocock-skills` を案内する。

状態遷移: 未ラベルの issue は普通まず `needs-triage`。そこから `needs-info`、`ready-for-agent`、`ready-for-human`、`wontfix` へ。`needs-info` は報告者が返信したら `needs-triage` に戻る。メンテナはいつでも上書きできる。見慣れない遷移はフラグを立て、進む前に聞く。

## 起動

メンテナが `/triage` を起動し、欲しいことを自然言語で述べる。解釈して動く。例:

- "Show me anything that needs my attention"
- "Let's look at #42"（issue または PR）
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## 注意が要るものを出す

issue tracker をクエリし、3 つのバケツを古い順に出す。

1. **Unlabeled**: 一度も triage していない。
2. **`needs-triage`**: 評価中。
3. **最後の triage メモ以降に報告者の活動がある `needs-info`**: 再評価が必要。

PR がスコープなら、これらのバケツに外部 PR を含め、各行に `[PR]` または `[issue]` を付ける。発見は *外部* PR だけ（誰が外部かは tracker 設定が定義する）。協力者の進行中 PR は triage 作業ではない。このフィルタは発見だけ。明示的に指名された PR は著者に関係なく必ず triage する。

件数と、項目ごとの 1 行要約を出す。メンテナに選ばせる。

## 特定の issue または PR を triage する

1. **文脈を集める。** issue または PR を全部読む（本文、コメント、ラベル、著者、日付。PR なら diff も）。以前の triage メモを解析し、解決済みの質問を聞き直さない。プロジェクトの用語集でコードベースを探索し、その領域の ADR を尊重する。コードベースに対して 2 つの確認を走らせる。(a) **冗長**: 要求された振る舞いの既存実装を、ドメイン概念で探す（要求の文言だけではない）。どこを見たか報告する。見つかったら already-implemented の `wontfix`（手順 5）。(b) **以前の却下**: `.out-of-scope/*.md` を読み、この要求に似たものを出す。

2. **推薦する。** メンテナにカテゴリと状態の推薦と理由、要求に関係するコードベース要約（すでに実装されているかを含む）を伝える。指示を待つ。

3. **主張を検証する。** grill する前に、主張が持つか確認する。バグなら報告者の手順から再現する。PR なら、diff が主張どおりか確認する。checkout し、関連テストまたはコマンドを走らせる。起きたことを報告する。確認できた（コードパス付き）、失敗、詳細不足（強い `needs-info` 信号）。確認できた検証は、ずっと強いエージェント brief になる。

4. **Grill（必要なら）。** 要求を肉付けする必要があるなら、Skill tool を 2 回呼ぶ。対象は `grilling` と `domain-modeling`。ラウンドごとに形を研ぎ、用語を鋭くし、判断が着地したら `CONTEXT.md` / ADR をその場で更新する。

5. **結果を適用する:**
   - `ready-for-agent`: エージェント brief コメントを投稿する（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`: エージェント brief と同じ構造。委任できない理由（判断、外部アクセス、設計判断、手動テスト）を書く。
   - `needs-info`: triage メモを投稿する（下のテンプレート）。
   - `wontfix` は issue を閉じる。コメントは *なぜ* で変わる:
     - **Already implemented**: 変更はすでにコードベースにある。場所を指す。`.out-of-scope/` には **書かない**（その KB は *却下された* 要求用であり、作済みのもの用ではない）。
     - **Rejected (bug)**: 丁寧に説明して閉じる。
     - **Rejected (enhancement)**: `.out-of-scope/` に書き、コメントからリンクし、閉じる（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`: ロールを付ける。部分的な進捗があれば任意でコメント。

## 状態の即時上書き

メンテナが "move #42 to ready-for-agent" と言ったら信じ、ロールを直接付ける。これからすること（ロール変更、コメント、close）を確認してから動く。grilling は飛ばす。grilling なしで `ready-for-agent` にするなら、エージェント brief を書くか聞く。

## Needs-info テンプレート

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

grilling 中に解決したことはすべて "established so far" に入れる。作業を失わない。質問は具体的で実行可能にする。"please provide more info" ではない。

## 前回のセッションを再開する

issue または PR に以前の triage メモがあれば読む。報告者が未解決の質問に答えたかを確認し、続ける前に更新した絵を出す。解決済みの質問は聞き直さない。
