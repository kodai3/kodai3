# Test-Driven Development

TDD は red → green のループ。このスキルは、そのループが残す価値のあるテストを生むための参照である。良いテストとは何か、テストをどこに置くか、アンチパターン、ループの規則。すべての節は毎サイクルで効く。ループの後ではなく、前と最中に読む。

コードベースを探索するときは `CONTEXT.md`（あれば）を読み、テスト名とインターフェースの語彙をプロジェクトのドメイン言語に合わせる。触る領域の ADR を尊重する。

## 良いテストとは

テストは公開インターフェース越しに振る舞いを検証する。実装詳細ではない。コードは丸ごと変わってよい。テストは変わらない。良いテストは仕様のように読める。「valid cart で checkout できる」は、存在する能力をそのまま言い、内部構造を気にしないのでリファクタに耐える。

例は [tests.md](tests.md)。モックの指針は [mocking.md](mocking.md)。

## Seam: テストを置く場所

**seam** は、テストする公開境界。中を覗かずに振る舞いを観察するインターフェース。テストは seam に置く。内部には置かない。

**事前に合意した seam だけでテストする。** テストを書く前に、対象の seam を書き出し、ユーザーと確認する。未確認の seam にテストは書かない。すべてをテストできるわけではない。seam を先に合意することで、テストの労力がクリティカルパスと複雑なロジックに載り、あらゆるエッジケースには散らない。

聞く: 「公開インターフェースは何か。どの seam をテストするか。」

そのインターフェースの形自体が争点なら（モジュールの深さ、seam の位置、露出すべきもの）、Skill tool で `codebase-design` を呼ぶ。module、interface、depth、seam、adapter、leverage、locality の共有語彙の出典である。回すセッションではなく、参照して読むもの。

## アンチパターン

- **実装結合**: 内部の協力者をモックする、private メソッドを試す、サイドチャネルで検証する（インターフェースではなく DB をクエリする）。兆候: 振る舞いが変わっていないのにリファクタでテストが壊れる。
- **同語反復**: アサーションが、コードと同じやり方で期待値を再計算する（`expect(add(a, b)).toBe(a + b)`、同じ手順で手計算したスナップショット、定数を自分自身と等しいと断言する）。構成上必ず通り、コードと不一致になれない。期待値は独立した真実から来る。既知のリテラル、計算例、spec。
- **水平スライス**: テストを全部書いてから実装を全部書く。まとめて書いたテストは *想像上の* 振る舞いを検証する。ユーザー向けの振る舞いではなく *形* を試し、本物の変化に鈍感になり、実装を理解する前にテスト構造にコミットする。代わりに **垂直スライス**: 1 テスト → 1 実装 → 繰り返し。各テストは直前のサイクルが教えたことに応答する **tracer bullet**。

## ループの規則

- **green の前に red。** 先に失敗するテストを書き、通す最小のコードだけ書く。将来のテストを先回りしない。投機的な機能を足さない。
- **1 スライスずつ。** 1 サイクルあたり seam 1 つ、テスト 1 つ、最小実装 1 つ。
- **リファクタはこのループに含めない。** レビュー段階（`code-review` スキル）の仕事であり、red → green の実装サイクルの仕事ではない。
