# UI Prototype

1 つのルート上に **構造的に大きく違う UI 案を複数** 作り、画面下のフローティングバーから切り替える。ユーザーはブラウザで案を切り替え、1 つを選ぶ（またはそれぞれから盗む）。残りは捨てる。

質問が見た目ではなくロジック / 状態なら、この枝は違う。[LOGIC.md](LOGIC.md) を使う。

## この形が合うとき

- 「このページはどう見えるべきか？」
- 「コミットする前に、このダッシュボードの案をいくつか見たい。」
- 「設定画面に別のレイアウトを試したい。」
- 頭の中の 3 つの曖昧なモックを 1 日かけて選ぶことになるとき。

## 2 つの下位形: 下位形 A を強く優先する

UI プロトタイプは、**アプリの残りにぶつかっている** ときに判断しやすい。本物のヘッダー、本物のサイドバー、本物のデータ、本物の密度。単独の捨てルートは真空。どの案も孤立ではよく見える。案を載せられる既存ページが妥当なら、既定は下位形 A。近くに家がないときだけ下位形 B。

### 下位形 A: 既存ページへの調整（優先）

ルートはすでにある。案は **同じルート上** に描き、`?variant=` URL search param でゲートする。既存のデータ取得、params、認証は残す。描画だけが入れ替わる。これが既定。やらない具体的な理由がなければこれを選ぶ。

まだページがないが *自然に既存ページの中に住む* もの（ダッシュボードの新しい節、設定画面の新しいカード、既存フローの新しいステップ）でも、下位形 A。ホストページの中に案を載せる。

### 下位形 B: 新しいページ（最後の手段）

プロトタイプ対象に、住む既存ページが本当にないときだけ（全く新しいトップレベル面、どこにも埋められないフローなど）。

プロジェクトがすでに使うルーティング慣例に従う **捨てルート** を作る。新しいトップレベル構造を発明しない。プロトタイプだと分かる名前（パスまたはファイル名に `prototype` を含める）。同じ `?variant=` パターン。

下位形 B にコミットする前に確認する: 本当に埋め込める既存ページはないか。空のルートは、人がいるページなら露わになる設計問題を隠す。

どちらの下位形でも、フローティングバーは同じ。

## 手順

### 1. 質問を書き、N を選ぶ

既定は **3 案**。5 を超えると構造的な違いではなくノイズになるので、そこで打ち切る。

計画を 1 行、プロトタイプの場所またはファイル先頭のコメントに書く:

> "設定ページの 3 案。`?variant=` で切り替え。既存の `/settings` ルート上。"

ユーザーが今反論しに来ていても、来ていなくても、これで動く。

### 2. 構造的に大きく違う案を作る

各案を草案する。それぞれを次に照らす:

- ページの目的と、アクセスできるデータ。
- プロジェクトのコンポーネントライブラリ / スタイルシステム（TailwindCSS、shadcn、MUI、プレーン CSS など）。
- 明確に export したコンポーネント名。例: `VariantA`、`VariantB`、`VariantC`。

案は **構造的に違う** 必要がある。違うレイアウト、違う情報階層、違う主アフォーダンス。色が違うだけではない。少しだけ違うカードグリッド 3 つは UI プロトタイプではなく壁紙。2 つの草案が似すぎたら、片方を "カードグリッドを使わない" という明示付きでやり直す。

### 3. つなぐ

ルート上に 1 つのスイッチャーを作る:

```tsx
// 擬似コード。プロジェクトのフレームワークに合わせる
const variant = searchParams.get("variant") ?? "A";
return (
  <>
    {variant === "A" && <VariantA {...data} />}
    {variant === "B" && <VariantB {...data} />}
    {variant === "C" && <VariantC {...data} />}
    <PrototypeSwitcher variants={["A", "B", "C"]} current={variant} />
  </>
);
```

下位形 A（既存ページ）: 既存のデータ取得はスイッチャーの上に残す。案ごとに変わるのは描画する部分木だけ。

下位形 B（新しいページ）: `/prototype/<name>` の捨てルートが同じスイッチャーを載せる。

### 4. フローティングスイッチャーを作る

画面下中央に固定した小さなバー。部品は 3 つ:

- **左矢印**: 前の案へ（循環）。
- **案ラベル**: 今の案キーと、案が名前を export していればその名前。例: `B (Sidebar layout)`。
- **右矢印**: 次へ（循環）。

振る舞い:

- 矢印クリックは URL search param を更新する（フレームワークのルータ。Next なら `router.replace`、React Router なら `navigate` など）。案は共有でき、リロードしても安定する。
- キーボード: `←` と `→` でも循環する。`input`、`textarea`、`[contenteditable]` にフォーカスがあるときは矢印キーを横取りしない。
- ページから視覚的に区別する（コントラストの高い pill、薄い影など）。評価中のデザインの一部ではないと分かるようにする。
- 本番ビルドでは隠す。`process.env.NODE_ENV !== 'production'` または同等のチェックでゲートする。迷い込んだプロトタイプマージがバーをユーザーへ出荷しないように。

スイッチャーは 1 つの共有コンポーネントに置き、両方の下位形が再利用する。プロジェクトの共有 UI が住む場所に置く。

### 5. 渡す

URL（と `?variant=` キー）を出す。ユーザーは届いたときにめくる。面白いフィードバックはたいてい **「B のヘッダーと C のサイドバーが欲しい」**。それが欲しい本物のデザイン。

### 6. 答えを残し、片付ける

勝った案が決まったら、答え（どの案か、なぜか）を残し、次にプロトタイプを [SKILL](SKILL.md) の手順で残す。勝者は本番コードへ折り込み、残りは main ではなく捨てブランチへ:

- **下位形 A**: 勝者を既存ページへ折り込む。負けた案とスイッチャーは main から落とす。
- **下位形 B**: 勝った案を本物のルートへ昇格する。捨てルートとスイッチャーは main から落とす。

案の一式は一次情報なので、ゴミ箱ではなく捨てブランチへ行く。main に残した案コンポーネントとスイッチャーはすぐ腐り、次の読者を迷わせる。

## アンチパターン

- **色やコピーだけ違う案。** それは微調整であり、プロトタイプではない。本物の案は構造で意見が分かれる。
- **案同士でコードを共有しすぎる。** 共有の `<Button>` はよい。共有の `<Layout>` は目的を壊す。各案はレイアウトを捨ててよい。
- **案を本物の mutation に配線する。** 読み取り専用でよい。案が mutation を必要とするなら stub を指す。質問は「どう見えるべきか」であり、「バックエンドは動くか」ではない。
- **プロトタイプをそのまま本番へ昇格する。** 案のコードはプロトタイプ制約（テストなし、最小のエラー処理）で書かれている。折り込むときはちゃんと書き直す。
