# Logic Prototype

誰でもボタンをクリックして状態モデルを運転できる、自己完結した 1 HTML ファイル（**共有可能なデモ**）。**ビジネスロジック、状態遷移、データの形** の問いに使う。紙の上では妥当に見えて、本物のケースを通すとしっくり来ない種類。

インストール不要の 1 ファイルなので、開発者でない人（デザイナー、PM、ドメイン専門家）に渡して、モデルを自分で感じてもらえる。だからコードの言語ではなく、その人の言語で話す。

## この形が合うとき

- 「この状態機械が X の次に Y のエッジケースを扱えるか分からない。」
- 「このデータモデルで、…のケースを本当に表せるか。」
- 「書く前に API の感触を知りたい。」
- 誰かが **ボタンを押して状態の変化を見たい** とき。

質問が「どう見えるべきか」なら、この枝は違う。[UI.md](UI.md) を使う。

## 手順

### 1. 質問を書く

コードを書く前に、どの状態モデルの、どの質問をプロトタイプするか書く。1 段落。デモの先頭（見える導入。コメントだけではない）。間違った質問に答えるロジックプロトタイプは純粋な無駄。ユーザーが今見ていても、後で AFK で戻ってきても、後から確認できるように質問を明示する。

### 2. ロジックを持ち運べるモジュールに隔離する

実際のロジック（問いに答えている部分）を 1 つの `<script>` ブロックに置き、小さな純粋モジュールとして書く。後で本番コードへ持ち上げて落とせる形。周りのページは捨てる。このモジュールは捨てない。

形は質問に依存する:

- **純粋な reducer**: `(state, action) => state`。アクションが離散イベントで、状態が 1 つの値のときに合う。
- **状態機械**: 明示的な状態と遷移。「今どのアクションが合法か」が質問の一部のときに合う。
- **プレーンなデータ型に対する小さな純粋関数の集合。** 暗黙の現在状態がなく、変換だけのときに合う。
- **明確なメソッド面を持つクラスまたはモジュール。** ロジックが継続する内部状態を本当に所有するとき。

ページへ配線しやすい形ではなく、*聞かれている質問* に最も合う形を選ぶ。純粋に保つ。DOM なし、`document` なし、ボタンハンドラが中へ手を伸ばさない。ページがこれに呼び込む。逆方向の流れはない。これが、プロトタイプを自分の寿命の先まで有用にする。質問が終わったら、検証した reducer / 機械 / 関数集合は、本番モジュールへ自分で持ち上がる。

### 3. 共有可能な HTML ファイルを作る

1 ファイル。プレーンな HTML / CSS / JS。フレームワークなし、bundler なし、サーバなし。すべてインライン。ダブルクリックで開き、メールで回しても生きる。開けば誰でも走らせられる。

開発者でない人向けに書く。すべてのラベルは **ドメイン言語**。コードではない。ボタンと状態は reducer ではなくビジネスのように読む。何が起きているかを平易な言葉で説明する。

上から下へ、きれいな階層:

1. **タイトルと 1 行の説明**。このデモが探らせるもの（手順 1 の質問）。
2. **Current state**: 関係する状態の全部。読めるパネル（ラベル付きフィールド。生 JSON ダンプではない）。クリックのたびに再描画し、変化が見える。開発者でない人が追いやすいなら、今変わったものを呼ぶ。
3. **Free-play ボタン**: アクションごとに 1 ボタン。常に使える。誰でも任意の順でモデルを突ける。クリックはアクションを dispatch し、状態を再描画する。
4. **ガイド付きウォークスルー**: **シナリオ** の集合。タブ 1 つにつき 1 つ。各タブはシナリオの短い平易な説明（セットアップする状況と、見るべきもの）を持ち、その下にそのシナリオの **押す順のボタン**。各ステップは本物のボタン。クリックがそのアクションを行い、次のステップへ進む。ウォークスルーを始めると既知の初期状態へリセットし、シナリオは毎回同じ走り方をする。

シナリオは、紙の上では考えにくいぎこちないケースを示す。ハッピーパス、厄介なエッジケース、違法であるべきことの試み。

美しさは抑えめ。きれいなタイポグラフィ、余裕のある余白、アクセント色は 1 つ。アニメーションなし、ギミックなし。状態とボタンと競合するものは置かない。

### 4. 渡す

ファイルを送るか、開いて見せる。ウォークスルーと free-play は、届いたときにクリックする。面白い瞬間は「待って、それは可能であるべきではない」や「えっ、X は違うと思っていた」。それは *アイデア* のバグであり、それが目的。新しいアクションや新しいシナリオが欲しければ足す。プロトタイプは進化する。

### 5. 答えとプロトタイプを残す

プロトタイプが問いに答えたら、答えを残し、次にプロトタイプを [SKILL](SKILL.md) の手順で残す。ロジック固有の対応: 検証した reducer / 機械 / 関数集合は本番モジュールへ持ち上がる（吸収された判断）。HTML の殻は、プロトタイプを一次情報として残す捨てブランチへ乗る。自己完結の 1 ファイルなので、そこで自明に再実行できる。

## アンチパターン

- **テストを足さない。** テストが要るプロトタイプは、もうプロトタイプではない。
- **本番 DB に配線しない。** 質問が永続化そのものでなければインメモリ状態。
- **一般化しない。** 「後で X を支えたくなったら」はない。プロトタイプは 1 つの問いに答える。
- **ロジックとページを混ぜない。** 純粋モジュールが DOM、`document`、ボタンハンドラを参照したら、もう持ち上がらない。ページは純粋モジュールの薄い殻。
- **フレームワーク、bundler、サーバに手を出さない。** 受け手がダブルクリックする 1 ファイル。React アプリや dev server は "共有可能" を壊す。
- **HTML の殻を本番へ出荷しない。** ページは手でクリックして進むことに最適化されている。残す価値があるのは、その裏のロジックモジュール。
