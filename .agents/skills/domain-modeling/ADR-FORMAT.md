# ADR の形式

ADR は `docs/adr/` に置き、連番にする: `0001-slug.md`、`0002-slug.md` など。

`docs/adr/` は遅延作成する。最初の ADR が必要になったときだけ作る。

## テンプレート

```md
# {判断の短いタイトル}

{1〜3 文: 文脈は何か、何を決めたか、なぜか。}
```

これで足りる。ADR は一段落でよい。価値は、判断が *あったこと* と *理由* を残すことにある。セクションを埋めることではない。

## 任意の節

本当に価値があるときだけ付ける。ほとんどの ADR には不要。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）: 判断を後から見直すときに有用
- **Considered Options**: 捨てた選択肢を覚えておく価値があるときだけ
- **Consequences**: 自明でない下流効果を明示する必要があるときだけ

## 番号

`docs/adr/` の既存最大番号を見て、1 増やす。

## ADR を提案する条件

次の 3 つがすべて真であること:

1. **戻しにくい**: 後から心変わりするコストが無視できない
2. **文脈なしでは意外**: 将来の読者がコードを見て「なぜこうなった」と思う
3. **本当にトレードオフがある**: まともな選択肢があり、理由を持って一つを選んだ

戻しやすいなら書かない。すぐ戻すからだ。意外でなければ誰も疑問に思わない。本当の選択肢がなければ、「当たり前のことをした」以上の記録にならない。

### 対象になるもの

- **アーキテクチャの形。** 「monorepo を使う。」「write model は event-sourced、read model は Postgres へ投影する。」
- **コンテキスト間の統合。** 「Ordering と Billing は同期 HTTP ではなくドメインイベントで話す。」
- **ロックインを伴う技術選択。** DB、メッセージバス、認証、デプロイ先。すべてのライブラリではない。入れ替えるのに四半期かかるものだけ。
- **境界とスコープ。** 「顧客データは Customer コンテキストが所有し、他は ID だけ参照する。」明示的な no は yes と同じくらい価値がある。
- **当たり前の道からの意図的な逸脱。** 「X のため ORM ではなく手書き SQL を使う。」妥当な読者が逆を仮定しそうなもの。次の人が「直して」しまわないようにする。
- **コードに見えない制約。** 「コンプライアンスのため AWS は使えない。」「提携 API の契約で応答は 200ms 未満。」
- **自明でない却下。** GraphQL を検討して微妙な理由で REST を選んだなら残す。残さないと半年後にまた GraphQL が出る。
