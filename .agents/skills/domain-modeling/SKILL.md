# Domain Modeling

設計しながら、プロジェクトのドメインモデルを能動的に作り、研ぐ。これは *能動的な* 規律である。用語を疑い、エッジケースのシナリオを作り、用語と判断が固まった瞬間に書き留める。（`CONTEXT.md` を語彙のために *読むだけ* は、このスキルではない。読むだけならどのスキルでも一行で足りる。このスキルはモデルを変えるときのものであり、消費するときのものではない。）

## ファイル構成

ほとんどのリポジトリは単一コンテキスト:

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

ルートに `CONTEXT-MAP.md` があるなら、複数コンテキスト。マップが各コンテキストの場所を指す:

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← システム全体の判断
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← コンテキスト固有の判断
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

ファイルは遅延作成する。書くものがあるときだけ作る。`CONTEXT.md` がなければ、最初の用語が固まったときに作る。`docs/adr/` がなければ、最初の ADR が必要になったときに作る。

## セッション中

### 用語集と突き合わせる

ユーザーが `CONTEXT.md` の既存言語と矛盾する用語を使ったら、その場で指摘する。「用語集では cancellation を X としているが、今の話は Y に聞こえる。どちらですか？」

### 曖昧な言葉を研ぐ

曖昧、または過負荷な用語を使ったら、正確な正規名を提案する。「account と言っていますが、Customer ですか User ですか。別物です。」

### 具体シナリオで議論する

ドメインの関係を話しているときは、具体シナリオでストレステストする。エッジケースを突くシナリオを作り、概念の境界をはっきりさせる。

### コードと突き合わせる

ユーザーが「こう動く」と言ったら、コードが同意するか確認する。矛盾があれば出す。「コードは Order 全体をキャンセルしているが、今は部分キャンセルが可能だと言いました。どちらが正しいですか？」

### CONTEXT.md をその場で更新する

用語が固まったら、その場で `CONTEXT.md` を更新する。溜めない。形式は [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。

`CONTEXT.md` に実装の詳細は一切入れない。spec でも、メモでも、実装判断の置き場でもない。用語集であり、それ以外ではない。

### ADR は出し惜しみする

次の 3 つがすべて成り立つときだけ ADR を提案する。

1. **戻しにくい**: 後から心変わりするコストが無視できない
2. **文脈なしでは意外**: 将来の読者が「なぜこうなった」と疑問に思う
3. **本当にトレードオフがある**: まともな選択肢があり、理由を持って一つを選んだ

どれか一つでも欠けるなら ADR は作らない。形式は [ADR-FORMAT.md](./ADR-FORMAT.md)。
