ユーザーが指定した固定点と `HEAD` の差分を、2 軸でレビューする。

- **Standards**: このリポジトリが文書化したコーディング規約に従っているか
- **Spec**: 元の issue / spec を忠実に実装しているか

両軸は **並列サブエージェント** で走らせ、互いのコンテキストを汚さない。このスキルがその結果を集約する。

issue tracker は渡されているはず。`docs/agents/issue-tracker.md` がなければ `/setup-matt-pocock-skills` を案内する。

## 手順

### 1. 固定点を固定する

ユーザーが言った固定点（commit SHA、ブランチ名、タグ、`main`、`HEAD~5` など）。指定がなければ聞く。

diff コマンドは一度だけ取る: `git diff <fixed-point>...HEAD`（三点。merge-base との比較）。コミット一覧も `git log <fixed-point>..HEAD --oneline` で取る。

先に進む前に、固定点が解決すること（`git rev-parse <fixed-point>`）と、diff が空でないことを確認する。悪い ref や空 diff は、2 つの並列サブエージェントの中ではなく、ここで失敗させる。

### 2. spec の出典を特定する

元の spec を、この順で探す。

1. コミットメッセージの issue 参照（`#123`、`Closes #45`、GitLab の `!67` など）。`docs/agents/issue-tracker.md` の手順で取得する。
2. ユーザーが引数で渡したパス。
3. `docs/`、`specs/`、`.scratch/` 以下で、ブランチ名または機能に合う spec ファイル。
4. 何も見つからなければ、spec の場所をユーザーに聞く。無いと言われたら **Spec** サブエージェントはスキップし、"no spec available" と報告する。

### 3. 規約の出典を特定する

コードの書き方を文書化しているもの。`CODING_STANDARDS.md` や `CONTRIBUTING.md` など。

リポジトリが文書化しているものに加え、Standards 軸は常に下の **smell baseline** を持つ。Fowler のコードスメル（_Refactoring_、第 3 章）の固定セット。リポジトリが何も文書化していなくても適用する。縛るルールは 2 つ:

- **リポジトリが勝つ。** 文書化された規約は常に優先する。baseline が指摘するものを規約が認めていれば、その smell は出さない。
- **常に判断。** 各 smell はラベル付きヒューリスティック（「possible Feature Envy」）であり、硬い違反ではない。ここでの規約と同様、ツールがすでに強制するものは飛ばす。

各 smell は *何か* → *直し方*。diff に当てはめる:

- **Mysterious Name**: 関数、変数、型の名前が、何をするか / 何を持つかを表していない。 → リネームする。正直な名前が浮かばないなら、設計が濁っている。
- **Duplicated Code**: 同じロジックの形が、変更の複数 hunk またはファイルに出る。 → 共有する形を抽出し、両方から呼ぶ。
- **Feature Envy**: メソッドが自分のデータより他オブジェクトのデータに手を伸ばす。 → 羨むデータの側へメソッドを移す。
- **Data Clumps**: 同じ数個のフィールドや引数が一緒に旅し続ける（生まれたがっている型）。 → 1 つの型にまとめ、それを渡す。
- **Primitive Obsession**: 独自の型を持つべきドメイン概念の代わりに primitive や string を使っている。 → その概念に小さな型を与える。
- **Repeated Switches**: 同じ型に対する同じ `switch` / `if` カスケードが変更の中で繰り返される。 → ポリモーフィズム、または両方の現場が共有する map に置き換える。
- **Shotgun Surgery**: 1 つの論理的変更が、diff の多数ファイルへ散らばった編集を強いる。 → 一緒に変わるものを 1 モジュールに集める。
- **Divergent Change**: 1 ファイル / モジュールが、無関係な複数理由で編集される。 → モジュールが 1 理由で変わるよう分割する。
- **Speculative Generality**: spec にない必要のための抽象、パラメータ、フック。 → 消す。本物の必要が出るまでインラインに戻す。
- **Message Chains**: 呼び出し側が依存すべきでない長い `a.b().c().d()`。 → 最初のオブジェクトの 1 メソッドの裏に隠す。
- **Middle Man**: ほとんど先へ委譲するだけのクラスや関数。 → 切り、本物の対象を直接呼ぶ。
- **Refused Bequest**: 継承したものの大半を無視または override するサブクラス / 実装。 → 継承をやめ、コンポジションにする。

### 4. 両サブエージェントを並列で起動する

**Standards サブエージェント** のプロンプトに含めるもの:

- 完全な diff コマンドとコミット一覧。
- 手順 3 で見つけた規約ソースファイルの一覧、**加えて手順 3 の smell baseline 全文**（サブエージェントはそれ以外から読めない）。
- ブリーフ: 「関連するファイル / hunk ごとに報告する。(a) diff が文書化された規約に違反する箇所: 規約（ファイル + 規則）を引用する。(b) 見つけた baseline smell: 名前を付け、hunk を引用する。硬い違反と判断を区別する。文書化された規約の違反は硬くてよいが、baseline smell は常に判断であり、文書化されたリポジトリ規約は baseline に勝つ。ツールが強制するものは飛ばす。400 語未満。」

**Spec サブエージェント** のプロンプトに含めるもの:

- diff コマンドとコミット一覧。
- spec のパス、または取得した本文。
- ブリーフ: 「報告する。(a) spec が求めたが欠けている、または部分的な要求。(b) spec が求めていない diff 上の振る舞い（scope creep）。(c) 実装されているように見えるが、実装が間違って見える要求。各指摘に spec の行を引用する。400 語未満。」

spec がなければ Spec サブエージェントはスキップし、最終報告にその旨を書く。

### 5. 集約する

2 つの報告を `## Standards` と `## Spec` の見出しの下に、原文または軽く整えて出す。指摘を **マージも再順位付けもしない**。2 軸は意図的に分離している（_なぜ 2 軸か_ を参照）。

最後に 1 行の要約: 軸ごとの指摘数と、*各軸の中で* 最悪の問題（あれば）。軸をまたいで 1 つの勝者を選ばない。分離が防ぐための再順位付けそのものになる。

## なぜ 2 軸か

片方に通って片方に落ちることがある。

- すべての規約に従うが、違うものを実装している → **Standards 通過、Spec 失敗。**
- issue が求めたことはそのままやるが、プロジェクトの慣例を破る → **Spec 通過、Standards 失敗。**

分けて報告すれば、片方の軸がもう片方を隠さない。
