# Codebase Design

**深いモジュール** を設計する。小さなインターフェースの裏に多くの振る舞いを置き、きれいな seam に置き、そのインターフェース越しにテストできる。コードを設計・再構成するときは、この言葉と原則を使う。狙いは、呼び出し側への leverage、保守者への locality、全員へのテストしやすさ。

## 用語集

これらの語をそのまま使う。"component"、"service"、"API"、"boundary" に置き換えない。一貫した言語が目的そのもの。

**Module**: インターフェースと実装を持つもの。スケールは問わない。関数、クラス、パッケージ、層を跨ぐスライス。_Avoid_: unit, component, service.

**Interface**: モジュールを正しく使うために呼び出し側が知らねばならないすべて。型シグネチャだけでなく、不変条件、順序制約、エラーモード、必要な設定、性能特性。_Avoid_: API, signature（型面だけを指すには狭い）。

**Implementation**: モジュールの中身、コード本体。**Adapter** とは別。小さな adapter に大きな実装（Postgres repo）も、大きな adapter に小さな実装（インメモリ fake）もありうる。話題が seam なら "adapter"。それ以外は "implementation"。

**Depth**: インターフェースにおける leverage。呼び出し側（またはテスト）が、学ばねばならないインターフェース単位あたりに行使できる振る舞いの量。小さなインターフェースの裏に大きな振る舞いがあるならモジュールは **深い**。インターフェースが実装と同じくらい複雑なら **浅い**。

**Seam** _(Michael Feathers)_: その場所を編集せずに振る舞いを変えられる場所。モジュールのインターフェースが *位置する* 場所。seam をどこに置くかは、その裏に何を置くかとは別の設計判断。_Avoid_: boundary（DDD の bounded context と衝突する）。

**Adapter**: seam でインターフェースを満たす具体物。*役割*（どのスロットを埋めるか）を言い、中身（何が入っているか）は言わない。

**Leverage**: 深さが呼び出し側に与えるもの。学ぶインターフェース単位あたりの能力。1 つの実装が N 箇所の呼び出しと M 個のテストに還元される。

**Locality**: 深さが保守者に与えるもの。変更、バグ、知識、検証が呼び出し側へ散らず、一箇所に集まる。一度直せば、どこでも直っている。

## 深いものと浅いもの

**深いモジュール** = 小さなインターフェース + 多くの実装:

```
┌─────────────────────┐
│   Small Interface   │  ← メソッド少、引数は単純
├─────────────────────┤
│                     │
│  Deep Implementation│  ← 複雑なロジックは隠す
│                     │
└─────────────────────┘
```

**浅いモジュール** = 大きなインターフェース + 少ない実装（避ける）:

```
┌─────────────────────────────────┐
│       Large Interface           │  ← メソッド多、引数は複雑
├─────────────────────────────────┤
│  Thin Implementation            │  ← ただ通すだけ
└─────────────────────────────────┘
```

インターフェースを設計するとき聞く:

- メソッド数を減らせるか
- 引数を単純にできるか
- より多くの複雑さを中に隠せるか

## 原則

- **深さは実装ではなくインターフェースの性質。** 深いモジュールの内部は、小さくモック可能で差し替え可能な部品で構成されてよい。それらはインターフェースの一部ではない。モジュールは **内部 seam**（実装に私的、自分のテストが使う）と、インターフェースの **外部 seam** の両方を持てる。
- **削除テスト。** モジュールを消したと想像する。複雑さが消えるなら、ただのパススルー。複雑さが N 箇所の呼び出し側に再出現するなら、存在価値がある。
- **インターフェースがテスト面。** 呼び出し側とテストは同じ seam を越える。インターフェースの *向こう* をテストしたくなったら、モジュールの形がたぶん違う。
- **adapter 1 つは仮定の seam。adapter 2 つは本物の seam。** 実際にそこでものが変わらないなら seam を入れない。

## テストしやすさのための設計

良いインターフェースはテストを自然にする。

1. **依存は受け取り、作らない。**

   ```typescript
   // テストしやすい
   function processOrder(order, paymentGateway) {}

   // テストしにくい
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **結果を返し、副作用を出さない。**

   ```typescript
   // テストしやすい
   function calculateDiscount(cart): Discount {}

   // テストしにくい
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **面は小さく。** メソッドが少ないほど必要なテストは少ない。引数が少ないほどテスト準備は単純。

## 関係

- **Module** は **Interface** をちょうど 1 つ持つ（呼び出し側とテストに見せる面）。
- **Depth** は **Module** の性質で、その **Interface** に対して測る。
- **Seam** は **Module** の **Interface** が位置する場所。
- **Adapter** は **Seam** に座り、**Interface** を満たす。
- **Depth** は呼び出し側に **Leverage** を、保守者に **Locality** を生む。

## 却下した枠組み

- **深さを実装行数 / インターフェース行数の比とする（Ousterhout）**: 実装の水増しを報いる。ここでは深さ = leverage。
- **"Interface" を TypeScript の `interface` キーワードやクラスの public メソッドとする**: 狭い。ここでの interface は、呼び出し側が知るべきすべての事実を含む。
- **"Boundary"**: DDD の bounded context と衝突する。**seam** または **interface** と言う。
